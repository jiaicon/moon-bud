# 智能助手 + 提醒固定动作 设计文档

日期：2026-10-23　状态：已批准（用户对下面 6 条选择说"按照你的想法来"，即全部按我倾向的定）

## 一句话意图

让家长**一只手也能把事情记下来**：说一句"下午三点瓶喂120毫升"就变成一条记录草稿，
建提醒时顺手指定"到点记什么"，到点弹框里点一下「记一笔」就直接落库。

## 为什么要做

现在的记一笔要走"打开表单 → 选类型 → 填字段 → 保存"，对抱着孩子的那位家长太长。
提醒这一侧更别扭：提醒说"该喂维生素D了"，点掉提醒之后还要自己走去记一笔、选用药、
把药名和剂量再敲一遍 —— 提醒里本来就写着这两样。

## 目标

1. 提醒可以携带一个**固定动作**（一种事件类型 + 一份预填值）。到点弹框多一个「记一笔」按钮，
   点一下按预填值 + 当前时刻直接生成记录；不带动作的提醒保持现在的单个「知道了」。
2. 一个自然语言输入口：一句话 → 解析成"记一笔草稿"或"新建提醒草稿"，**预填进现有表单**，人点确认才落库。
3. 解析用 DeepSeek，成本按现在的定价（`deepseek-flash` 输入 1 元/百万 token 闲时、输出 4 元）
   一次约 0.002 元，一天 100 次是每月几分钱量级，所以不需要为省钱做本地降级。

## 非目标

- 不做对话式助手（没有多轮上下文、没有闲聊、没有育儿问答）。它只是"一句话 → 一条结构化草稿"。
- 不做语音输入。
- 不让模型直接写库，也不让模型决定"要不要保存"。
- 不做厂商推送通道那一类已有独立结论的事（见推送设计文档）。

## 反目标（做错了就失败的点）

- **不往健康记录里造数字。** 体温、身高体重、奶量、药名剂量这些真实测量值，绝不给默认值。
  要出现在一键记录里，只能是人建提醒时自己填过的那一份。
- **不把"记一笔"变成一个需要思考的决定。** 点下去如果还要回答一个问题，这一枪就白做。
- **不让 AI 不可用时比现在更差。** 没网、没 key、模型乱回，助手入口退化成一个普通输入框 + 明确提示，
  其余路径（手动记一笔、手动建提醒）一点不受影响。

## 约束

- DeepSeek key 只存在于服务器 `.env`（用户长期指令：不进仓库、不贴聊天）。**绝不进 APK 或 H5 产物**，
  所以调用必须在 NestJS 侧完成。
- 服务端目前没有任何出网 HTTP 依赖（`apps/api/package.json` 无 axios/got；源码里 `fetch(` 零命中）。
  Node 自带 `fetch`，不新增依赖。
- 模型输出必须过 zod 校验才出接口；接口返回的是草稿，不是已保存的数据。
- 时间一律"墙钟串 + 账号时区"，由客户端已有的 `src/utils/wall-time.ts:isoFromWallTime` 转 UTC。
  模型不参与时区换算。
- 游客态：记一笔和提醒都会写库，所以助手入口和「到点顺手记」对游客静默隐藏 —— 不弹窗、不引导（既有裁定）。
- 每次真机验证要等一次云打包，所以能不在客户端做的都放服务端。

## 数据模型

### 提醒侧（新增两列，一个迁移）

```prisma
model Reminder {
  /// 到点顺手记的事件类型；null = 这条提醒没有动作，弹框保持单个"知道了"。
  /// 取值必须落在 @moonbud/shared 的 EVENT_TYPES 里，由 DTO 校验（库里不加枚举，避免改类型要迁移）。
  eventType    String?
  /// 该动作的预填 payload。约定只有一种状态：要么 null，要么已经过该类型的完整 zod 校验。
  actionPayload Json?
}
```

- 两列都可空、无默认，老数据不用回填：老提醒就是"没有动作"。
- `actionPayload` 存之前用该 `eventType` 的 zod schema 过**完整校验**（不是 `partial`），不合法就 400。
  于是这一列只有两种状态：**要么 null，要么本身就是一份能直接落库的预填**。
  （原设计写的是"宽松校验、允许不完整"，2026-10-23 落地时改的：`eventPayloadSchemas[type]` 的静态类型是
  `ZodTypeAny`，对它调 `.partial()` 运行时并不存在（`growth` 那张是 `strict().refine()`）；而"完整才存"
  恰好就是弹框两态要的那个判据。不完整的那一半不必入库 —— 建提醒那一格当场就不发 payload（见交互一节），
  存半份只会造出一个"看起来有动作、到点却记不进"的东西。）
- 更新提醒时 `eventType`/`actionPayload` 可以置 `null` 取消动作；改了 `eventType` 就把旧的
  `actionPayload` 一起清掉（不同字段的形状对不上）。

### 记录侧（新增两列，同一个迁移）

```prisma
model Event {
  /// 一键生成的来源提醒：留着当出处，编辑后也不清（统计"哪些提醒真的在起作用"要用）。
  fromReminderId String?   @db.Uuid
}
```

- `fromReminderId` 不加外键级联：提醒删掉之后记录要留着，出处字段可以指向一个已不存在的提醒。
- **原来想的「补一下」标记（`needsFill`）砍掉了。** 它只有两种定义法，都不成立：
  "缺必填" —— 缺必填的那条根本不会一键生成（见下面的判定规则），列永远为 false；
  "缺非必填" —— 几乎每条一键生成的记录都缺非必填项，标记等于没有。一个要么不亮、
  要么常亮的徽标不是功能。想补细节的人本来就能点进记录编辑。

### 通知列表响应（不加列）

到点弹框现在只认得 `occurrenceId`（`NotificationDto`，`api-types.ts:142-151`），认不出背后的提醒。
不在 `Notification` 上加列 —— 在通知列表接口里按 `occurrence.reminderId → reminder` join 出
动作信息放进响应 DTO。写通知的那条 cron 本来就知道 reminder，但**读的时候算**比
存一份冗余更不容易说谎。

**落地形状（2026-10-23）**：暴露的不是平铺的 `reminderId` + `eventType`，而是嵌套的
`action: { reminderId, childId, eventType, payload } | null`（`NotificationDto.action`）。
理由：一键记一笔需要 `childId` 和整份 `payload`，平铺两个字段的话客户端得为列表里每一行再发一次
"取这条提醒的详情" —— 那是不可接受的。`action === null` 就是"这条没有动作"，弹框与通知中心据此
画一个按钮或什么都不画；`payload === null` 是"只带类型"，按钮叫「去记一笔」。

## 交互

### 建提醒：多一格「到点顺手记」

- 一个可选的类型选择（复用记一笔那张类型网格的图标和文案），不选就是没有动作。
- 选了之后，下面内联展开该类型的字段 —— **只列必填项**（`events/event-fields.ts` 的 `requiredFields`）。
  非必填项不在这填，因为这一格的目的不是"提前把记录写完"，而是"到点那一枪不用再问人"。
- 必填项留空**允许**保存，但界面上要说实话（见下面的判定规则）。

**「到点直接记」还是「到点打开记一笔」—— 判定规则只有一个：**
把 `actionPayload` 拿去过该类型 `@moonbud/shared` 的**完整** schema（不是 `partial`）。
过 = 一键能落库；不过 = 跳表单让人补。这一条自证：

- 用药缺 `name`/`dose` → 完整 schema 不过 → 跳表单。
- 生长发育的 refine 要求"体重/身高/头围至少一项"，而 `requiredFields` 是空的 → 空 payload 不过 → 跳表单。
  **所以"必填项为空"的类型（睡眠、生长发育）不会误判成"能直接记"** —— 这条规则替我们处理了
  `requiredFields` 与 schema 不一致的那些情况，不需要一张类型白名单。
- 睡眠的空 payload 过完整 schema（字段全可选）→ 直接记，落一条"某个时刻开始睡"，这本身是有意义的记录。

落地之后这条规则分两段执行：**写入时**（建提醒那一格 + 服务端 DTO）用完整 schema 判，不过就不存 payload；
**到点时**（弹框、通知中心）只需看 `action.payload` 是不是 null —— 因为库里那一列按上面的约定只有 null
和完整两种状态。客户端因此不许自己重跑 zod，只读服务端的结论。

### 到点弹框

`due-watch.ts` 现在用 `uni.showModal`，只有确认/取消两个按钮 —— 刚好够，不自研弹层：

| 场景 | 标题 | 确认按钮 | 取消按钮 |
| --- | --- | --- | --- |
| 单条到点、无动作 | 到点了 | 知道了（唯一按钮，`showCancel:false`） | — |
| 单条到点、有动作且过完整 schema | 到点了 · 该喂药了 | **记一笔** | 知道了 |
| 单条到点、有动作但 schema 不过 | 同上 | **去记一笔**（跳表单，类型和已知字段带上） | 知道了 |
| **多条同时到点** | N 条提醒到点 | 知道了（唯一按钮） | — |

- **合框那一条不改**（`dueWatchMessage` 的多条分支）：一屏里让人在两条提醒之间挑一个来记，
  正是"把点一下变成一个决定"这个反目标要防的事。批量到点时这一框只报数，
  动作入口在通知中心页（见下）逐条摆着。
- 点「记一笔」= 用 `actionPayload` + 当前时刻 POST 一条事件，走已有的出箱（`outboxStore.submitCreate`），
  所以断网时它进"待同步"而不是失败。
- 点完不再弹任何东西（不 toast 庆祝、不追问），标记那条通知已读。

### 通知中心页的每一行也带这个动作

到点弹框只覆盖"恰好盯着屏幕"那一次：冷启动那轮是刻意**只记底不弹**的
（`due-watch.ts:24-27`），多条会合框，进程划掉了更是根本弹不出来（实测：离线那条是真丢了、不补发）。
所以「记一笔」不能只活在弹框里。`pages/notification-center/index.vue` 的每一条到点通知
（`occurrenceId !== null`）右侧带同一个动作按钮，规则与弹框一致（无动作就没有按钮，schema 不过就显示「去记一笔」）。
这一块不额外要数据：通知列表接口本来就 join 出 `action`。

### 系统通知栏那一条点下去落到哪 —— 一期刻意不变

状态栏里的推送（云函数那条）点击走 `notifications/push-client.ts` → `routing.ts` 的分流：
有 `occurrenceId` 就落到提醒列表的 ACTIVE 栏。**它不会直接进弹框，也不会直接记一笔**，这一期没改它。

- 为什么不动：动作的判定只有一个来源 —— 通知列表接口 join 出来的 `action`（见上面"落地之后这条规则分两段执行"）。
  推送的透传体里没有 `eventType`，也没有"这个孩子还可不可写"的结论；要在点击回调里直接落库，
  就得让服务端把整份预填塞进推送体，还要在冷启动会话没落地时自己判 —— 那正是本期消掉的那类客户端猜测。
- 人从状态栏进来以后仍有出口：提醒列表 → 通知中心那一行的芯片，走同一套判定。
- 真机清单（BUILD.md 第 9 节）里有一条专门验这个落点没被改坏。

### 一键写不下去的时候

归档中的孩子服务端会 400（`events.service.ts` 的 `assertChildWritable`），而出箱对非 401 的确定性错误
是"重试 8 次再丢" —— 那意味着点下去什么也没发生，八次以后才来一句"已放弃"。不能这么留：

- 客户端本来就握着 `ChildDto.archivedAt`（`stores/child.ts`），**点之前先判**：孩子不可写就不给「记一笔」，
  这一行退化成「去记一笔」，由表单用它现成的方式说清楚为什么不能记。
- 「恢复网络后才发现不可写就立即 drop」**第一期不做**（2026-10-23 落地时的裁定）。判据只能是 HTTP 400
  的状态码，而 400 里也藏着真正的数据错误，据它丢弃会把人记下的东西吃掉；现有行为（重试后放弃 + 一句提示）
  不是新造的缺陷。客户端在**点之前**拦已经覆盖这条路径的绝大多数，剩下的竞态是"离线期间家长把孩子归档了"，
  代价是一条待同步被放弃并说明。
  **若以后要真解决，正确做法是让服务端为归档返回可区分的状态码，不是在客户端猜 400。**

### 助手（第二期）

- 入口位置：首页顶部一条"说一句话"的输入条（已裁定，见下面记录）。
- 输入一句话 → 服务端返回草稿 → 跳进对应的现有表单并预填（记一笔表单已支持 `?type=`，
  `event-form/index.vue:130-164`；提醒表单需要补同样的预填参数）。
- 解析结果里如果模型认为信息不足（没说时间、类型认不出来），**不猜**：回一个"要建什么类型"的草稿，
  把能确定的字段带上，缺的留空让人补。

## 服务端解析接口

`POST /assistant/parse`（鉴权：登录用户；输入：`{ text: string }`，长度上限 200 字）

输出契约（zod 校验后才出接口）：

```jsonc
{
  "intent": "event" | "reminder" | "unknown",
  "event":     { "type": "...", "occurredAtWallClock": "YYYY-MM-DDTHH:mm", "payload": { } },
  "reminder":  { "title": "...", "type": "ONE_TIME|RECURRING",
                 "dueAtWallClock": "...", "rrule": "...",
                 "eventType": "...", "actionPayload": { } }
}
```

- 时区由服务端按 `User.timezone` 告诉模型"现在的墙钟时间和时区"，模型只回墙钟。
- 用 `response_format` 的 JSON 模式或工具调用的 `strict` 通道；提示里带完整枚举和每种类型的必填字段。
- 节流：每个用户每分钟 N 次（配置项），超出回 429。注册口没有验证码，助手口是个能白嫖算力的面。
- 失败（超时、非 2xx、校验不过）→ 明确错误码，客户端显示"这句我没看懂，手动记一下"，
  **不静默降级成猜测**。

## 成本与配额

- 模型：`deepseek-flash`。一次约 1k 输入 token + 150 输出 token ≈ 0.0016 元（闲时）。
- 忙时（工作日 9:00–12:00、14:00–18:00）翻倍，仍然可忽略。
- 上下文 1M、输出上限 384K 对我们毫无意义，不需要 v4-pro（贵 4.5 倍）。
- 唯一要防的是被刷，所以节流和"必须登录"是硬要求。

## 分期

**第一期（不依赖 AI，可独立上线）**：提醒固定动作 + 到点「记一笔」（弹框与通知中心两处入口）。
纯本地数据模型与交互，零成本、零外部依赖，云打包一次就能验。

**第二期**：`POST /assistant/parse` + 助手输入口 + 预填跳转。依赖第一期定下的
`eventType`/`actionPayload` 形状（模型输出要能直接喂给提醒表单）。

## 裁定记录（2026-10-23，全部按我的倾向定，用户说"按照你的想法来"）

1. **助手入口放哪**：我倾向首页顶部一条"说一句话"的输入条（最快，且它是"快速记录"该有的位置），
   而不是"我的"页里一个二级菜单。代价：首页多一行，且游客要静默隐藏。
2. **一键记录用谁的 occurredAt**：当前时刻，不是提醒的应到时刻。理由：家长点"记一笔"通常是喂完才点，
   也可能是提前喂完 —— 应到时刻是个谎言。代价：拖延半小时就记成半小时后。
3. **提醒带动作但孩子为空**：家庭级提醒（`childId` 为 null）不允许带动作，因为记录必须有 `childId`。
   代价：想给"全家"设的带动作提醒做不到。
4. **模型能不能指定动作类型**：能（"每天9点提醒吃维生素D400IU" → 用药 + 预填 name/dose），
   但同样只进草稿，人确认。
5. **通知中心那一行的「记一笔」是我在写文档时补的**（原来只有弹框）。理由：弹框只覆盖"正盯着屏幕"，
   而冷启动刻意不弹、多条会合框、进程划掉了根本弹不出来。代价：一个按钮 + 一条已经要 join 的字段。
   **定了：留着**，第一期就做。
6. **「补一下」标记砍了**（原来打算给一键生成的记录挂个小徽标）。理由见数据模型那节：
   它要么永远不亮，要么几乎每条都亮。代价：少一个"回头补细节"的提示。

## 这份文档没覆盖、计划要补测试的输入

- 模型返回不存在的类型名 / 越界的数字 / 中文全角数字 / 空 payload。
- 提醒的 `actionPayload` 与 `eventType` 不匹配（改了类型没清 payload 的路径）。
- `requiredFields` 为空但 schema 有 refine 的类型（生长发育）→ 必须判成"跳表单"而不是"直接记"。
- 多条同时到点：弹框只有一个「知道了」，不出现任何动作按钮。
- 到点弹框点「记一笔」时归档中的孩子 —— 点击前就被挡住。（"断网排队、恢复后才发现不可写要立即 drop"那条已裁定不做，见上一节。）
- 断网点「记一笔」→ 出箱 → 恢复网络后重放，`fromReminderId` 要跟着走。
- 同一提醒连续两枪（重复提醒每天一次）不能互相覆盖出处。
- 模型接口 429 与超时的客户端表现必须不同于一句"失败了"。

## 二期落地时的补记（2026-10-26，实现与文档不同的地方以这一节为准）

- **模型名以 env 为准**：`DEEPSEEK_MODEL` 默认 `deepseek-flash`，代码里只是兜底。
  模型名是上游会改的东西，写死等于每改一次发一次版；上游拒名时改服务器 `.env` 一个值。
  同理 `DEEPSEEK_BASE_URL`（默认 `https://api.deepseek.com`）。
  `DEEPSEEK_API_KEY` 空（trim 后）时装配的是 `NoopAssistantProvider`，启动日志写
  「助手通道：未配置 DEEPSEEK_API_KEY，一句话记录不可用」——**没有密钥不是崩溃，是一个明确的 503**。
- **节流的默认值与实现**：每用户每分钟 **6** 次（`ASSISTANT_RATE_LIMIT`，`<1` 或非法值退回 6），
  实现是**单容器进程内的滑动窗口 Map**，不建表：建表要迁移、要进 e2e 的 TRUNCATE 名单，
  代价是重启清零而收益是零（这一条防的是白嫖算力，不是审计）。
  超出回 429 + `{ code: 'ASSISTANT_RATE_LIMITED', message: '说得有点快了，等一分钟再试' }`。
- **负载整份清空，不逐栏裁**：模型给的 `payload`/`actionPayload` 过不了 zod 时，
  这一份置成 `{}` 并在 `dropped` 里记下是哪一份，而**不是**逐栏挑出能留的。
  逐栏要在 shared 里再维护一张字段清单，而 `event-types.ts` 已经是那张清单——两份清单迟早对不上
  （一期终审那一串 bug 就是两份判定不一致的产物）。
- **错误码表定下来**（文档原来只写"明确错误码"）：429 `ASSISTANT_RATE_LIMITED`、
  503 `ASSISTANT_UNAVAILABLE`、502 `ASSISTANT_TIMEOUT` / `ASSISTANT_BAD_OUTPUT`，
  响应体统一 `{ code, message }`，message 是中文一句，客户端直接念它
  （`ApiRequestError.message`），客户端**不重跑 zod**、只读服务端给出的结论。
- **`dropped` 的去向（2026-10-26 存在感 v1 改了口径）**：一期把它念在首页的 toast 里，人已经跳走了，
  那句话在说哪一栏没人知道。现在 `dropped` 随草稿一起进本地交接（`PickedEvent.dropped` /
  `PickedReminder.dropped`），由表单顶部那条横幅说实话；首页不再提它。
  仍然只有**一处**产文案的地方（`assistant/ask-flow.ts` 的 `askBannerCopy`），表单只负责摆它。
- **信封是"恰好一个槽"**（终审补）：`intent` 说了 event 就必须只带 event——两个槽都填、
  或 unknown 还带负载，都在共享契约这一层判坏。客户端按 `intent` 分支取负载，
  多带的那一半会静不吭声地消失而 `dropped` 是空的，屏幕上那句"已按你说的话填好"就成了谎话。
- **周期规则只允许界面摆得出来的那几种**（终审补，代码是 `isFaithfulRrule`）：
  `FREQ=DAILY[;INTERVAL=n]`、`FREQ=WEEKLY;BYDAY=单个日子`、`FREQ=MONTHLY;BYMONTHDAY=1`，
  外加 `BYHOUR/BYMINUTE`。一周挑几天、`FREQ=HOURLY`、每月 15 号这类一律判坏。
  理由：客户端的 `parseRruleForUi` 只认第一个 BYDAY、忽略 INTERVAL/BYMONTHDAY，
  而服务端排期用的是原样那份规则——屏幕写"每周一"、实际周一周三都响。
  提示词里的例子和这把尺子由同一个测试钉住，两边不许各写各的。
- **`errors` 只进日志，而且日志里没有用户原话**（终审补）：净化失败时给出的每条是
  `栏目: 错误码`，只有我们自己写的那句中文（custom issue）带文字。zod 的默认文案会把
  收到的原值念出来（`received '刚刚瓶喂 120 毫升'`），而那句话是要留在手机里的东西。
- **周期草稿的钟点只能从 `rrule` 读回来**（终审补）：`RECURRING` 的 `dueAtWallClock` 合法地为 null，
  交接给表单的那份草稿因此只有 `rrule`、没有 date/time；表单的"几点"那一格必须用 `parseRruleForUi` 的
  `hour/minute` 覆盖，否则它停在打开页面的那一刻，而保存又按它重拼规则——提醒永远在那个钟点响。
- **草稿不走 URL，走本地一次性交接**（2026-10-26 真机乱码后补，代码是 `src/assistant/draft-handoff.ts`）：
  一期把标题、`type`、date/time、`actionPayload` 全塞进 `navigateTo` 的 query，真机上标题显示成
  `%E5%AE%9D%E5%AE%9D…`。根因是平台的不对称：App 端每个 `navigateTo` 都会把 query 的**值**再
  `encodeURIComponent` 一遍（`@dcloudio/uni-app-plus` 的 `encodeQueryString`），而 `onLoad` 的 options
  只解一层；H5 因为 vue-router 多解了一层，所以浏览器里永远看不出问题。
  修法是把 url 从这条链路上去掉而不是"按平台多解一次"：首页 `stageDraft()` 存进 storage，
  表单 `onLoad` 取一次即删（`takeEventDraft` / `takeReminderDraft`），跳转 url 只剩页名。
  三条口径：草稿的意图与当前页不匹配时**不消费**（留给另一张表单）；存放超过 **10 分钟**视为过期并删除
  （否则第二天进来会被昨天的那句话预填）；编辑那一路（带 `id`）**不取草稿**，两头不能互相盖。
  代价：预填不再是"能用 url 直接复现"的状态，真机验证清单一节因此补了第 8 步（中文必须是汉字）。

## 助手存在感 v1 的补记（2026-10-26）

用户的原话是「这个助手存在感太低了」。二期那一版把入口做成首页一栏带 placeholder 的输入框，
结果没人知道那里能说话——**入口的失败不是找不到，是看不出它能用**。这一节的三条都以实现为准：

- **三个入口，一个面板，三处是同一颗右下角胶囊。** 首页、记录页、提醒页各有一颗 `.ask-pill`
  （`position: fixed` + `right: 40rpx`）：首页坐在 FAB 那一格 `bottom: calc(var(--window-bottom) + 40rpx)`，
  记录页与提醒页在其上再让出一个 FAB 身位（`+ 108rpx + 16rpx`）。
  **首页第一版是内容区顶部的实心块（`.ask-entry`，主色块 + 一行例句），当天就改掉了**：内容会滚，
  滚过一格就等于没有；而三处长得一样，人才认得出"那是同一个能力"。
  三处点开的都是同一个 `components/AskSheet.vue`：调用、判断 intent、交接、跳转只在这一处发生一次。
  每页各写一遍就是三份会各自漂移的判定——这条由 `pages/__tests__/list-ask-pill.test.ts` 钉，
  三颗胶囊的样式由 `home-ask-entry.test.ts` 逐字比对（剥掉注释与 `bottom` 后必须完全相同）。
- **"没听懂"留在原地问，不换页。** `intent` 为 unknown 时不再 toast 一句"没看懂"，面板里直接问
  "这句我没能判断，您想让我做哪一件？"，给「记一笔 / 设提醒」两个 chip；点一下带着 `intentHint`
  把**同一句话**再发一次。服务端把 `intentHint` 拼进系统提示词（`prompt.ts` 的「【人已确认】」那一段），
  它只锁意图、不放松"没说就留 null"那一句。DTO 用 `@ValidateIf(..., value !== undefined)` + `@IsIn(['event','reminder'])`：
  `@IsOptional()` 会放 `null` 穿过去，而 null 不是确认过的意图。
  反问的那一步绝不换页、绝不清空人打过的字——把人带去一张空表单比留在原地更坏。
- **横幅取代跳转前的 toast。** 表单顶部那条（`.ask-banner`）只在真取到草稿时出现，编辑那一路（带 `id`）
  根本不走它；文案是 `askBannerCopy(dropped)`：什么都没丢才允许说"填好了"，丢了任何一栏就只说"没填上"。
- **例句是功能清单，不是散文。** `ASK_EXAMPLES` 恰好三句、每句 ≤30 字、两种意图各有覆盖，
  且**不许**出现"今天喝了多少奶"这类这一期还答不出来的问句（`assistant/__tests__/ask-flow.test.ts` 钉死）。
  点一句就是替人说完整句并直接发送。
- **刻意没做的**：例句不逐条念 `dropped` 的字段名（要念就得在客户端再维护一张"路径→栏目名"的表，
  而 `event-types.ts` 已经是那张表）；面板不做语音输入；入口不做游客态（游客口径是点击静默、不弹窗，
  一个点开只会说"先登录"的入口比没有入口更坏）。
